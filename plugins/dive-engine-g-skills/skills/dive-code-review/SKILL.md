# 代码审查

当任务是在 `dive-engine-g` 中执行 CR，或在提交前检查是否存在明显问题时，使用此 skill。

## 目标

从代码评审视角给出高价值结论：

1. 优先识别 bug、行为回归与高风险改动
2. 检查幂等、风控、发奖、回调与持久化链路是否被破坏
3. 检查测试是否覆盖新增行为
4. 检查是否违反国际化军规
5. 输出可执行的修复建议，而非泛泛结论

## 优先检查的内容

- `models/service/task.go`：任务编排、锁、状态流转、回调
- `engine/engine.go`：算奖、发奖、撤回主流程
- `engine/param/*`：参数加载与占位符替换
- `engine/calculator/*`：计算逻辑
- `engine/reward/*`：发奖与撤回逻辑
- `engine/risk/*`：风控与异步通知
- `models/service/message.go`：回调、通知、重试消息
- `dao/calc/*`：状态与明细持久化

## 审查顺序

### 1. 先看影响范围

先判断改动属于哪一层：

- 参数层
- 计算层
- 风控层
- 发奖层
- 服务编排层
- 持久化层
- 回调与通知层

如果改动跨层，优先检查链路拼接处，而不是先看局部实现细节。

### 2. 优先找高风险问题

重点检查：

- 任务幂等是否被破坏
- 风控执行顺序是否变化
- reward sender 是否可能重复发放
- 边界条件与异常分支（如发奖失败）处理是否完备
- 是否违反滴滴国际化军规（skill: `didi-code-jungui`）
- recall 是否遗漏状态更新
- compute 成功但 reward 未触发的分支
- callback 或 MQ 重试是否退化
- `FusionOnly`、`onlyWriteNotRead` 等分支是否被误伤

### 2.1 发奖异常专项检查（多发 / 少发 / 不发）

**此为关键检查项，必须逐一确认：**

#### 多发场景检查

- **重复发奖**：检查 sender 是否正确实现幂等判断（如 coupon.go 中 `existInCache` 检查）
- **重试触发多发**：检查 MQ 重试、callback 重试时是否会重复调用 `Reward` 而绕过状态检查
- **分布式锁失效**：检查 `task.go` 中锁的 key 是否唯一、过期时间是否合理、锁释放是否正确
- **并发竞争**：检查是否存在多个实例同时处理同一任务的可能
- **状态回退**：检查是否有分支可能导致 `TaskStatusSuccess` 被错误重置为 `TaskStatusRun`
- **风控绕过**：检查是否存在分支跳过 `IsCheat` 检查直接发奖
- **部分成功后重试**：检查批量发奖部分成功时，重试是否会导致已成功的奖励重复发放

#### 少发场景检查
- **发奖列表被错误覆盖**：检查 `task.Reward` 是否在中间环节被错误清空或覆盖
- **filter 拦截逻辑错误**：检查

- **状态提前标记成功**：检查是否在发奖前就将状态标记为 `TaskStatusSuccess`
- **部分失败整体回滚**：检查批量发奖时部分失败是否导致整体状态失败，进而影响成功的奖励`engine/filter` 是否误拦截了应发的奖励
- **风控误拦截**：检查 `Pass` 方法返回 `false`（不放行）的场景是否合理
- **参数加载失败**：检查 `param.Load` 失败时是否有默认值或补偿逻辑
- **calculator 计算遗漏**：检查计算器是否遗漏了应得的奖励类型

#### 不发场景检查

- **异常分支未处理**：检查所有 error 返回后是否正确终止流程并记录状态
- **静默失败**：检查是否存在 `err != nil` 但未向上透传的情况
- **空奖励列表**：检查 `len(task.Reward) == 0` 的分支是否合理
- **cheat=true 后无补偿**：检查反作弊拦截后是否有用户通知或人工复核机制
- **DB 写入失败**：检查 `InsertOrUpdate` 失败时是否有重试或告警
- **缓存不一致**：检查 Fusion/Redis 与 MySQL 数据不一致时的处理
- **NoticeReward 失败**：检查异步通知失败是否影响发奖状态（应不影响，但需确认）

#### 关键代码路径逐一验证

发奖主链路：`Compute → IsCheat → Reward → Send → NoticeReward`

| 阶段 | 检查点 | 多发风险 | 少发风险 | 不发风险 |
|------|--------|----------|----------|----------|
| Compute | 计算结果缓存 | 重复计算 | - | 计算失败 |
| IsCheat | Pass 返回值 | 返回 true 放行 | - | 返回 false 拦截 |
| IsCheat | err 处理 | - | - | err != nil 终止 |
| Reward | 锁与状态检查 | 锁失效 | - | 已成功跳过 |
| Reward | filter 拦截 | - | 误拦截 | - |
| Send | sender 幂等 | 无幂等检查 | - | - |
| Send | 部分成功 | 重试多发 | - | - |
| NoticeReward | MQ 失败 | - | - | 通知丢失 |

#### 风控钩子一致性检查

新增风控实现时，必须对比同类实现：

- `Pass` 方法错误时返回值：应为 `(true, err)` 还是 `(false, err)`
- `Reward` 方法：是否正确处理空数据、是否忽略 MQ 失败
- `Recall` 方法：是否正确更新状态、是否通知下游
- 数据路径：`common_id_list.order_id_list` vs `metrics.order_list` 等是否与上游一致

### 3. 检查契约一致性

确认以下契约是否仍然一致：

- calculator 配置名与 param name 是否一致
- reward type 注册值是否与业务配置匹配
- risk 注册的 `biz + rewardType` 是否准确
- 下游结构是否与第三方契约一致
- mock、日志与状态码语义是否仍然成立

### 4. 检查测试缺口

若存在新增行为，至少判断是否覆盖以下场景：

- 正常路径
- 异常路径
- 边界输入
- 幂等或重试路径
- recall 或通知路径

### 5. 输出格式

输出时遵循：

- 先列发现的问题，并按严重级别排序
- 每条问题说明影响、原因、触发条件
- 明确指出缺失的测试或验证
- 若未发现问题，明确写“未发现阻塞性问题”，并补充残余风险

### 6. 提交前快速流程（整合版）

当用户诉求是“准备提交 / 先做 CR / commit 前检查”时，按以下最小流程执行：

1. 收集上下文：
   - `git status --short`
   - `git diff --staged`
   - 必要时补充 `git diff`
2. Findings 优先：
   - 行为回归
   - 注册点遗漏
   - MQ / callback / Apollo 同步遗漏
3. 存在高优先级问题时，先修复再提交。

补充说明：

- 仓库当前未启用自动 pre-commit CR hook，提交前检查以人工 CR 为主。
- 仅当用户明确要求“CR agent / 子代理 / 并行 review”时，才启用独立 review agent；否则主 agent 直接做静态 review。

## 完成标准

一次代码审查仅在以下条件都满足时才算完成：

- 已覆盖主要改动层级
- 已检查主链路风险点
- 已说明测试是否充分
- 输出结论可直接指导修改或放行

结束时要明确说明：按照 `dive-code-review` 技能完成执行。
